PART 2 — WHAT WAS FIXED IN THIS PASS
==================================================================

[DONE + LIVE] FIX 1 — Stale demo availability (was review #1 finding F3)
   Problem: all 10 demo consultants had availability entirely in May 2026 (in
   the past). The booking panel filters to future slots only, so every demo
   profile showed "Свободните часове се подготвят" with zero bookable hours —
   the opposite of "looks full".
   Fix: added scripts/refresh-example-availability.cjs. It scans the
   consultants table, and for rows with isExample === true ONLY, rewrites
   `availability` to future weekday slots (next ~2 weeks, weekends skipped),
   preserving each profile's original hour-of-day pattern, and recomputes
   `nextAvailable`. Real profiles are never touched. Safe-by-default (dry-run
   unless --apply).
   Applied to production DynamoDB (owner-approved). Verified via live API:
   all 11 public profiles now have a future nextAvailable (earliest 2026-06-08)
   and 10–40 future slots each. This is live immediately (data is fetched at
   runtime), no redeploy required.
   Reversible: DynamoDB point-in-time recovery is enabled; re-runnable any time.

[DONE — staged, not yet deployed] FIX 2 — og:image leaked external demo URLs (F4)
   Problem: demo profiles' social/SEO images pointed at randomuser.me stock
   photos (e.g. og:image = randomuser.me/...men/32.jpg). README intent is that
   SEO/social images stay branded/stable.
   Fix: scripts/site-build.mjs now only trusts images hosted on the GrowPoint
   site host or *.amazonaws.com for SEO. External/demo hosts and signed S3 URLs
   fall back to the branded default (assets/advertisement/3.jpg).
   Verified: regenerated the committed GitHub Pages route HTML — og:image,
   twitter:image AND JSON-LD ImageObject for all 10 demo profiles now use the
   branded image. The real Менторски profile was already branded (unchanged).
   STATUS: the fix is staged in the working tree (consultants/*/index.html +
   sitemap.xml). It goes live only after commit + push to the GitHub Pages
   branch. Not pushed (left to the owner).

[DONE — staged, not deployed by owner choice] FIX 3 — CloudFront per-route SEO (F1)
   Problem: CloudFront served the generic home <title> for ALL routes,
   including known consultant slugs. Two root causes:
     (a) build:cloudfront did not render per-route static HTML into dist/.
     (b) The distribution uses a private S3 REST origin (OAC). default_root_object
         only resolves "/", so "/consultants/foo/" hit S3 as a missing key,
         got 403/404, and the custom_error_response fell back to the generic
         root /index.html — losing per-route metadata.
   Fix (two parts):
     (a) scripts/site-build.mjs: build:cloudfront now renders the per-route
         index.html files into dist/ (renderStaticRoutes: true). Verified —
         dist/consultants/<slug>/index.html etc. are emitted with correct
         per-route metadata.
     (b) infra/terraform/main.tf: added a CloudFront Function (viewer-request,
         cloudfront-js-2.0) that rewrites directory-style URIs to their
         index.html object ("/x/" -> "/x/index.html", "/x" -> "/x/index.html",
         leaving files with extensions alone), and associated it with the
         default cache behavior. Unknown routes still 404 at S3 and fall back to
         the SPA shell, so SPA fallback is preserved. terraform validate passes.
   STATUS: NOT applied to AWS (owner chose to keep this local for now). To
   deploy: see PART 4.
